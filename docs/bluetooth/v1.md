# Robine Wake Bluetooth contract v1

This document is the compatibility boundary between the Robine Wake firmware and
native clients. Version 1 is additive: implementations must ignore unknown JSON
fields. A breaking change requires a new contract version and, if the transport
itself changes, a new GATT service UUID.

Security is intentionally `none` for the feature prototype. The contract reserves
space for later pairing and authenticated requests; it must not be presented as a
secure control channel in version 1.

## GATT service

| Role | UUID | Properties |
| --- | --- | --- |
| Robine Wake service | `8AD00001-A7A9-4EF7-A259-67C9C65E4C10` | Primary service |
| Command | `8AD00002-A7A9-4EF7-A259-67C9C65E4C10` | Write with response |
| Response | `8AD00003-A7A9-4EF7-A259-67C9C65E4C10` | Read |

## Commands

The command characteristic accepts one UTF-8 JSON object terminated by `\n`.
The firmware may receive that object over several GATT writes and limits a command
to 65,536 bytes.

```json
{"v":1,"id":"client-generated-uuid","op":"state.get","body":{}}
```

- `v` is the contract version.
- `id` is generated by the client and echoed in the response.
- `op` is a namespaced operation.
- `body` is always an object. Mutating an existing alarm requires its current
  `revision`; stale writes fail instead of silently overwriting a newer edit.

Successful response:

```json
{"v":1,"id":"client-generated-uuid","status":"ok","body":{}}
```

Error response:

```json
{"v":1,"id":"client-generated-uuid","status":"error","error":{"code":"stale_revision","details":{}}}
```

Clients branch on `error.code`, never on a human-readable message.

## Paged response transport

Each read of the response characteristic returns at most 480 bytes. Every page
starts with this 20-byte big-endian header:

| Offset | Size | Field |
| ---: | ---: | --- |
| 0 | 2 | ASCII magic `RW` |
| 2 | 1 | Transport version (`1`) |
| 3 | 1 | Flags; bit 0 means final page |
| 4 | 4 | Response sequence number |
| 8 | 2 | Zero-based page index |
| 10 | 2 | Page count |
| 12 | 4 | Total JSON byte length |
| 16 | 4 | CRC32 of the complete JSON payload |
| 20 | ≤460 | Page payload |

The client rejects mixed sequences, missing or duplicated pages, inconsistent
metadata, invalid lengths, and CRC mismatches before decoding JSON. It reads until
the final flag is present and the received page count and total length agree.

## Version 1 operations

- `capabilities.get`
- `state.get`
- `alarm.create`, `alarm.update`, `alarm.delete`, `alarm.preview`, `alarm.trigger`
- `session.get`, `session.snooze`, `session.dismiss`
- `settings.smartphone_dismiss.set`
- `clock.confirm`, `camera.calibrate`
- `hue.pair`, `hue.refresh`, `hue.disconnect`
- `breathing.start`, `breathing.stop`
- `history.erase`, `device.factory_reset`

The BLE state payload is a purpose-built client DTO, not a serialization of the
firmware's internal processes. Audio files, diagnostics archives, and firmware
images remain Wi-Fi transfers; BLE is the nearby configuration and control plane.

`alarm.trigger` starts the exact same wake-session state machine as a scheduled
alarm. It carries no `test` flag: session controls and dismissal semantics are
therefore identical for manual tests and real wake-ups. While visible, clients may
poll the lightweight `session.get` operation to expose stop and snooze controls.

`settings.smartphone_dismiss.set` accepts `{"enabled":true|false}`. The command
is rejected with `smartphone_dismiss_setting_locked` while a wake session is
active. `state.get` exposes `smartphone_dismiss.enabled` and
`smartphone_dismiss.locked`; active session DTOs expose the permission captured
at start as `smartphone_dismiss_allowed`. When false, `session.dismiss` is
rejected with `smartphone_dismiss_disabled`.

`hue.pair` accepts `{"bridge_host":"192.168.1.42"}` after the physical Hue
Bridge link button has been pressed. `state.get` exposes only non-secret Hue
status plus the available room and zone targets; the bridge application key is
never returned to a client.

`breathing.start` accepts a grouped-light `target_id`, a supported
`duration_minutes`, and an optional `volume_percent` from 0 to 100. It starts a
device-owned 4-second inhale / 6-second exhale loop using native Hue transition
durations. `breathing.volume` changes `volume_percent` during an active session
while preserving its inhale/exhale gain envelope. `breathing.stop` is idempotent
and restores the target state captured at start. `state.get` exposes the current
phase and volume under `hue.breathing`.

Alarm payloads may contain this additive object:

```json
{
  "light_profile": {
    "enabled": true,
    "target_id": "hue-grouped-light-resource-id",
    "target_name": "Chambre",
    "start_brightness": 1,
    "end_brightness": 70,
    "ramp_seconds": 900,
    "end_behavior": "restore"
  }
}
```

`end_behavior` is one of `restore`, `off`, or `leave`. Unknown additive alarm
fields remain subject to the normal version 1 compatibility rule.

## HTTP mirror and client routing

`POST /api/v1/command` accepts and returns the exact same JSON envelopes as the
Bluetooth command boundary. In the security-zero prototype this endpoint has no
HTTP authentication or CSRF requirement. The `state.get` response advertises
reachable URLs in `body.transport.http_endpoints`.

Clients persist a URL learned through Bluetooth and prefer HTTP for subsequent
commands. A connection error, timeout, or non-2xx HTTP response falls back to BLE
with the same request identifier. After fallback, the next Bluetooth `state.get`
refreshes the saved address, allowing recovery after DHCP address changes.

The firmware keeps a bounded cache of request identifiers shared by both
transports. Replaying the same envelope returns the original response without
executing it twice. Reusing an identifier with a different envelope returns
`request_id_reused`. This makes a response-lost HTTP → BLE retry safe for mutations.

### Server-Sent Events

Clients open `GET /api/v1/events` with `Accept: text/event-stream`. The server
sends `ready`, `state.changed`, and `session.changed` events plus a comment
heartbeat every 15 seconds. Event IDs are monotonic within a boot and the last 64
events are replayable through `Last-Event-ID`. The iPhone performs a focused
`session.get` or `state.get` only after an event; it never polls on a timer.
